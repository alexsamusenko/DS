# Обзор проекта: назначение и описание каждого модуля

Этот документ — техническое описание того, что уже реализовано в репозитории, для человека, который открывает проект впервые. Соответствие уровням архитектуры — артефакт «Архитектура DS» (диаграммы, L0–L6); формальные постановки — `docs/chapter2/`.

## Идея проекта одной фразой

Сквозной конвейер обработки слабоструктурированных агрономических данных: семантическая интеграция разнородных источников (онтология) → восстановление пропусков в пространственно-временных рядах → мультимодальный прогноз урожайности с объяснением → оптимизация дифференцированного внесения удобрений → доступ ко всему через единый API.

## `src/ds_ontology/` — семантическая интеграция (L2)

**Назначение.** Реализует формальную модель `O_t = ⟨C, R_O, R_D, Ax, I, τ⟩` (§2.1): классы предметной области (Поле, Культура, ПоказательПочвы, ПогодноеСобытие, АгроПриём, ВредительБолезнь, Источник), отношения между ними, и функцию интеграции `μ = φ ∪ λ`, превращающую разнородные наблюдения в триплеты графа знаний вокруг конкретного экземпляра `Поле`.

| Файл | Роль |
|---|---|
| `schema.py` | TBox: определяет 7 классов (`owlready2.Thing`), 7 объектных отношений, атрибуты и аксиому дизъюнктности классов. Функция `build_schema()` возвращает готовую онтологию в изолированном `owlready2.World` |
| `integration.py` | ABox: функции `get_or_create_pole`, `assert_soil_reading`, `assert_weather_event`, `assert_agro_priem` (реализация `φ`) и `resolve_entity_mention` (реализация `λ` — связывание текстового упоминания с существующим экземпляром по строковому сходству и аннотации `regionalnoe_nazvanie`) |
| `build.py` | Демонстрационная сборка: один экземпляр `Поле`, показания сенсора, лабораторный анализ, погодное событие, агроприём и текстовое упоминание — показывает, что `μ` действительно связывает разнородные источники в общий граф |

**Пример использования:**
```python
from ds_ontology.schema import build_schema
from ds_ontology.integration import get_or_create_pole, assert_soil_reading, get_or_create_istochnik

onto = build_schema()
pole = get_or_create_pole(onto, pole_id="7", region="Ростовская область")
istochnik = get_or_create_istochnik(onto, tip="IoT-датчик почвы")
assert_soil_reading(onto, pole, tip_pokazatelya="влажность почвы", znachenie=27.4,
                     data_izmereniya="2026-05-14", edinitsa_izmereniya="%", istochnik=istochnik)
```

## `src/ds_preprocessing/` — комбинированная предобработка (L3)

**Назначение.** Восстанавливает пропуски в матрице «участок × время» одного показателя, комбинируя пространственную оценку (кригинг) и временную (полиномиальный тренд) по обратной дисперсии (§2.2).

| Файл | Роль |
|---|---|
| `anomaly.py` | `detect_anomalies()` — MAD на остатках после снятия тренда (не на сырых значениях — важно для нестационарных рядов, §2.2.2) |
| `spatial.py` | `spatial_estimate()` — обыкновенный кригинг (`pykrige.OrdinaryKriging`) по срезу одного момента времени |
| `temporal.py` | `temporal_estimate()` — полином по ряду одной точки, дисперсия — через leave-one-out (не по остаткам на обучении — иначе завышенная уверенность из-за переобучения) |
| `combine.py` | `fill_gaps()` — главная точка входа: детекция аномалий → обе оценки → взвешивание по обратной дисперсии → явный флаг невосстановимых ячеек |
| `validation.py` | `validate_inputs()` — проверка форм, типов, NaN среди «наблюдаемых», дублирующихся координат. Вызывается на входе в `fill_gaps()` |
| `synthetic.py` | Контролируемое поле с известной пространственной и временной структурой + функция маскирования для проверки качества восстановления |
| `build_demo.py` | Сравнение RMSE трёх методов (пространственный/временной/комбинированный), усреднённое по нескольким случайным маскам |

**Пример использования:**
```python
from ds_preprocessing import fill_gaps
result = fill_gaps(coords, times, values, mask_observed)
# result["filled"], result["unrestored"], result["anomalies"]
```

## `src/ds_prediction/` — мультимодальный прогноз (L4)

**Назначение.** Прогноз урожайности по вектору признаков, собранному из четырёх модальностей (num/geo/img/text, §2.3.2), с ансамблевой моделью и SHAP-интерпретацией по модальностям.

| Файл | Роль |
|---|---|
| `features.py` | `MODALITY_COLUMNS` — таксономия признаков по модальностям; `select_modalities()`, `modality_of()` |
| `synthetic.py` | Многолетний многополевой набор со скрытым «эффектом плодородия» поля (создаёт реалистичную внутриполевую корреляцию, из-за которой случайное разбиение train/test завышало бы качество) |
| `model.py` | `train_model()`, `evaluate_grouped_cv()` — `GroupKFold` по `field_id`, а не случайное разбиение (§2.3.5) |
| `explain.py` | `modality_importance()` — SHAP (`shap.TreeExplainer`), агрегация `Σ|φ_j|` по модальности (§2.3.4) |
| `build_demo.py` | Сравнение RMSE полной модели с моделями без одной модальности + таблица вклада по SHAP |

**Пример использования:**
```python
from ds_prediction import train_model, select_modalities, modality_importance, MODALITY_COLUMNS
model = train_model(df)
importance = modality_importance(model, select_modalities(df, MODALITY_COLUMNS.keys()))
```

## `src/ds_optimization/` — оптимизация внесения (L5)

**Назначение.** Для каждого элементарного участка поля находит дозу удобрения, максимизирующую прибыль, с учётом прогноза L4 как базового потенциала урожайности (§2.4).

| Файл | Роль |
|---|---|
| `response.py` | `yield_response()` — кривая Митчерлиха (закон убывающей отдачи): `Y(d) = baseline + R·(1 - e^{-d/s})` |
| `economics.py` | `profit()` — прибыль на единицу площади при заданной дозе |
| `optimize.py` | `optimize_unconstrained()` — аналитическое решение из условия первого порядка; `optimize_with_budget()` — метод Лагранжа с бисекцией по теневой цене бюджета |
| `validation.py` | Проверка цен, диапазона доз, столбцов таблицы участков, достижимости бюджета |
| `synthetic.py` | Разнородные участки: дефицит азота одновременно снижает базовый потенциал и повышает отклик на удобрение — источник содержательной неоднородности |
| `build_demo.py` | Сравнение дифференцированного сценария с равномерным при одинаковом суммарном расходе |

**Пример использования:**
```python
from ds_optimization import optimize_with_budget
doses = optimize_with_budget(plots_df, budget=1000.0, dose_min=0, dose_max=150,
                              price_yield=1300.0, price_fert=50.0)
```

## `training/` — дообучение моделей (L1)

**Назначение.** Скрипты дообучения для задач, где решено использовать специализированную модель, а не LLM (§2.5, `docs/chapter2/model_training.md`).

| Файл | Роль |
|---|---|
| `finetune_ner.py` | Дообучение RuBERT для NER (культура/агроприём/показатель/вредитель). Два режима: продовый (`--train/--eval`, реальная модель `DeepPavlov/rubert-base-cased`) и `--smoke-test` (офлайн, программно генерируемый корпус `generate_synthetic_corpus()` на шаблонах и словарях реальных агротерминов, случайно инициализированная мини-BERT-модель — huggingface.co недоступен из текущей песочницы) |
| `finetune_leaf_classifier.py` | Дообучение EfficientNet-B0 для классификации поражений листа. Продовый режим — `ImageFolder` с реальными данными (PlantDoc, CC BY 4.0, `docs/governance/licenses.md`); `--smoke-test` — процедурно генерируемые синтетические изображения (`SyntheticLeafDataset`), т.к. предобученные веса ImageNet тоже недоступны из песочницы |

Оба скрипта проверены end-to-end в этой сессии: NER сходится с F1=0 до F1=1.0 за ~20 эпох на корпусе из 500 сгенерированных предложений; классификатор поднимает валидационную точность с уровня случайного угадывания (0.25 для 4 классов) до ~0.55 за 20 эпох на 1200 синтетических изображениях.

## `service/` — единый API (L6)

**Назначение.** FastAPI-обёртка над L3–L5: каждый маршрут вызывает уже протестированную функцию `src/ds_*`, не добавляя собственной логики.

| Файл | Роль |
|---|---|
| `app.py` | Сборка приложения, подключение роутеров, `/health`, CORS для dev-фронта (localhost:5173), монтирование собранного `frontend/dist/` статикой (если она собрана — см. `frontend/README.md`) |
| `schemas.py` | Pydantic-модели запросов/ответов — валидация входа до вызова доменного кода |
| `routers/preprocessing.py` | `POST /preprocessing/fill-gaps` → `ds_preprocessing.fill_gaps` |
| `routers/prediction.py` | `POST /prediction/predict`, `GET /prediction/training-summary` → `ds_prediction` (модель кешируется в памяти процесса после первого запроса) |
| `routers/optimization.py` | `POST /optimization/optimize` → `ds_optimization` (с бюджетом или без, в зависимости от тела запроса) |
| `routers/training_stats.py` | `GET /training/history` — читает `build/{ner_model,leaf_classifier}/history.json`, которые `training/finetune_*.py` пишут по завершении обучения; ничего не запускает сам |
| `routers/datasets.py` + `datasets_catalog.py` | `GET /datasets` (сопоставляет `docs/dataset_cards/*.md` с содержимым `data/`), `POST /datasets/upload` (распаковывает `.zip` в `data/<name>/`, с проверкой path traversal и лимитом размера) |

Запуск: `python3 -m uvicorn service.app:app --reload` → документация на `http://localhost:8000/docs` (автогенерируется из Pydantic-схем, ничего не написано вручную).

## `frontend/` — веб-интерфейс поверх `service/`

**Назначение.** React + TypeScript SPA (Vite): три вкладки без клиентского роутера — статистика обучения (графики по `GET /training/history`), тест прогноза на точке (форма → `POST /prediction/predict` → прогноз + вклад модальностей по SHAP), каталог датасетов (`GET /datasets` + форма загрузки через `POST /datasets/upload`). Графики — `recharts`, без дополнительных UI-библиотек.

Дев-режим — два процесса (backend на 8000, Vite dev-сервер на 5173 с hot reload). Production-сборка (`npm run build` → `frontend/dist/`) отдаётся тем же `service/app.py` с того же порта — `Dockerfile` собирает её двухстадийно (`node:20-slim` только на стадии сборки, в финальном образе Node нет). Подробности — `frontend/README.md`.

## `tests/` — что проверяется

65 тестов на момент написания: `test_schema.py` (L2, включая проверку консистентности ризонером HermiT), `test_preprocessing.py` (L3, включая валидацию входа), `test_prediction.py` (L4, включая утечку данных между полями в `GroupKFold`), `test_optimization.py` (L5, включая формальное доказательство превосходства дифференцированного внесения через 15 комбинаций параметров), `test_service.py` (API, каждый маршрут проверяется на содержательный результат, а не только код ответа), `test_frontend_api.py` (каталог датасетов, статистика обучения, загрузка архива включая отказ на path traversal и некорректное имя).

## `docs/` — что где искать

- `docs/chapter2/` — формальные постановки (математика, критерии качества) для текста диссертации.
- `docs/governance/` — реестр лицензий и принятые отраслевые практики; обязателен к обновлению при добавлении любого нового внешнего актива.
- `docs/datasets.md` — открытые источники данных по уровням архитектуры.
- `docs/model_cards/`, `docs/dataset_cards/` — карточки моделей/датасетов (шаблоны, дополняются по мере использования реальных данных в главе 4).
