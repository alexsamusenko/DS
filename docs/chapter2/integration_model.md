# 2.6. Слой интеграции с внешними информационными системами (L7)

> Черновик раздела главы 2 диссертации. Реализует уровень L7 архитектуры (см. артефакт «Архитектура DS») — доступность результатов работы системы (в первую очередь L5, карта-задание) для внешних SaaS и информационных систем агрохолдингов, а не только для собственного интерфейса (frontend/).

## 2.6.1. Постановка задачи

Практическая ценность системы ограничена, если её результаты остаются внутри неё самой: агрохолдинг, как правило, уже эксплуатирует собственную FMIS (farm management information system) и/или парк техники с бортовыми терминалами. Задача уровня L7 — не заменить эти системы, а сделать выход L5 (`{(k, d_k^*)}` — соответствие «участок → доза», §2.4.6) **потребляемым** ими без ручного переноса данных.

Формально, пусть `Ω` — внутреннее каноническое представление результата (набор Pydantic-моделей `service/schemas.py`, уже используемых во всех остальных уровнях). Задача L7 — определить набор отображений

```
ψ_j : Ω → F_j,   j = 1..M
```

где `F_j` — формат/протокол обмена, понятный внешней системе `j`. В данной работе реализовано два таких отображения, соответствующих двум принципиально разным классам внешних потребителей:

- **`ψ_REST`** — произвольная внешняя SaaS/ИС общего назначения (агрохолдинговая ERP, дашборд, скрипт интеграции) — канал: HTTP/JSON по контракту OpenAPI (уже существующий `service/`, формализуется здесь как канал L7, а не только как «свой» API);
- **`ψ_ISOXML`** — бортовые терминалы техники и FMIS, поддерживающие стандарт ISOBUS — канал: файл ISO 11783-10 Task Data (`TASKDATA.XML`), пригодный для загрузки на терминал независимо от производителя техники.

Два канала не конкурируют, а закрывают разные сценарии: `ψ_REST` — для систем, которые сами тянут/принимают данные программно; `ψ_ISOXML` — для физического переноса карты-задания на технику (в т.ч. без постоянного сетевого соединения — файл на USB/карте, стандартный сценарий на практике, см. §1.4.2 про работу без гарантированного интернета).

## 2.6.2. Канал 1: REST/OpenAPI как универсальный контракт

Требование к `ψ_REST` — не конкретный протокол, а **формальность и самоописываемость** контракта: любая внешняя система должна получить машиночитаемое описание входа/выхода без чтения исходного кода. FastAPI генерирует его автоматически из тех же Pydantic-схем, что валидируют вход (`service/schemas.py`) — то есть контракт (`GET /openapi.json`) гарантированно не расходится с реализацией (в отличие от отдельно поддерживаемой документации, которая может устареть).

Это делает `ψ_REST` пригодным для любой внешней ИС, способной говорить HTTP/JSON — конкретный агрохолдинг может как дёргать `POST /optimization/optimize` напрямую (передавая свои данные по участкам вместо демонстрационных), так и опрашивать `GET /integration/export-isoxml` (§2.6.3) для получения файла в формате ниже.

## 2.6.3. Канал 2: экспорт в ISO 11783-10 (Task Data / ISOXML)

ISO 11783 (ISOBUS) — действующий международный стандарт обмена данными между сельскохозяйственной техникой и системами управления; часть 10 определяет формат `TASKDATA.XML` для карт-заданий (в т.ч. переменного нормирования, VRA). Он выбран как целевой формат `ψ_ISOXML` не произвольно, а потому что именно его — по построению, а не по соглашению с конкретным производителем — понимают бортовые терминалы техники разных вендоров, что и обеспечивает интероперабельность без частных коннекторов под каждую систему агрохолдинга.

Отображение `ψ_ISOXML(Ω)` строит документ с иерархией `TASKDATA → CTR (хозяйство) → FRM (ферма) → PFD (участок/поле) → TSK (задание) → TZN (зона обработки) → PDV (значение показателя, доза)`, где:

- каждому участку `k` из результата L5 соответствует один `PFD`/`TZN` с геометрией (полигон) и значением `PDV`, полученным из `d_k^*`;
- геометрия полигона в прототипе — **синтетическая** (регулярная сетка с шагом, производным от площади `a_k`, см. `src/ds_integration/geometry.py`), т.к. в текущей системе нет источника реальных границ полей (кадастр/ГИС хозяйства не подключены, см. `docs/datasets.md` про задачу 6) — это явное упрощение, не незамеченное допущение;
- числовой код показателя (DDI — Data Dictionary Identifier, ISO 11783-11) для «дозы внесения» требует финальной сверки с официальным реестром AEF ISOBUS DDI перед использованием с реальной техникой конкретного производителя — отмечено как открытый пункт в `docs/governance/licenses.md`, а не как подтверждённый факт.

## 2.6.4. Связь с реализацией

`src/ds_integration/`: `isoxml_export.py` (`ψ_ISOXML` — построение `TASKDATA.XML` из результата L5 через `xml.etree.ElementTree`, без новых зависимостей), `geometry.py` (синтетическая полигональная геометрия участков для демонстрации, см. §2.6.3), `build_demo.py`. `service/routers/integration.py`: `POST /integration/export-isoxml` — принимает тот же `OptimizeRequest`, что и `/optimization/optimize` (§2.4), дополнительно оптимизирует дозы и сразу возвращает готовый `TASKDATA.XML`.

## Выводы

Раздел 2.6 формализует то, что практическая ценность результата L5 (карта-задание) реализуется полностью только при его доступности вне собственного интерфейса системы: REST/OpenAPI закрывает произвольные программные интеграции с ИС агрохолдинга, ISO 11783-10 — интеграцию с бортовыми терминалами техники по действующему отраслевому стандарту, независимо от производителя. Оба канала переиспользуют уже формализованный и протестированный результат L5, не дублируя его логику.
