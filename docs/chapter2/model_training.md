# 2.5. Стратегия применения моделей: дообучение, промптинг, function calling

> Черновик методологического раздела главы 2. Обосновывает выбор конкретных моделей и подходов (дообучение против промптинга LLM) для каждого модуля, где решение неочевидно и требует явного обоснования, а не единообразного применения одного инструмента ко всем задачам.

## 2.5.1. Принцип: задача определяет инструмент, а не наоборот

Ошибочный по умолчанию подход — применять языковую модель (LLM) равномерно везде, где встречается неструктурированный вход. Правильная постановка вопроса для каждой точки интеграции: **является ли вход задачи открытым (произвольным, не перечислимым заранее) или закрытым (фиксированный, заранее известный набор классов/сущностей)**. Для закрытых задач специализированная классическая модель, обученная на размеченных данных именно этой задачи, при достаточном объёме разметки превосходит LLM по точности, стоимости инференса и предсказуемости — и не требует внешнего API. LLM обоснована только там, где вход принципиально открытый.

## 2.5.2. Матрица решений по модулям

| Модуль | Задача | Тип входа | Решение | Обоснование |
|---|---|---|---|---|
| L1, фото | Детекция вредителей/болезней по изображению листа | Закрытый (конечный список классов поражений) | **Классификатор (EfficientNet/ResNet), дообученный на PlantVillage-подобном датасете** — не LLM/VLM | Специализированная модель точнее на узкой задаче, работает локально на телефоне/дроне без API, даёт калиброванную вероятность класса, а не текст, который нужно парсить |
| L1, фото (расширение) | Локализация нескольких очагов поражения на одном фото | Закрытый, но с локализацией | YOLO-детектор — **только если появятся bbox-размеченные данные** (PlantVillage — классификация целого листа, не детекция; для детекции нужен датасет вроде PlantDoc) | Технически некорректно обучать детектор на классификационной разметке — это два разных типа аннотаций (см. `docs/governance/licenses.md` про PlantVillage) |
| L1, текст/голос | NER: извлечение сущностей (культура, приём, доза, вредитель) | Закрытый (сущности соответствуют классам онтологии, §2.1.3) | **Дообученный RuBERT-классификатор токенов**, обучающий корпус размечается вручную (100-200 предложений, `docs/datasets.md`), без обязательного LLM-bootstrap | Корпус достаточно мал для ручной разметки; дообученная модель на порядки дешевле в проде и не зависит от внешнего API |
| L2 | `resolve()`/λ — связывание синонимов и упоминаний | Полу-открытый (сходство термина с известным словарём) | Эмбеддинг-модели (не генеративная LLM) | Задача семантического сходства, не генерации |
| L2 | Эволюция онтологии — кандидаты новых терминов (`ΔC_t`) | Открытый, но редкий | Гибрид: классический фильтр новизны (частотность + расстояние до ближайшего класса по эмбеддингу) отсеивает большинство случаев бесплатно; LLM/человек — только для прошедших фильтр | Минимизирует число обращений к LLM до действительно неоднозначных случаев |
| L4 | Прогноз урожайности | Закрытый (табличные признаки) | Ансамбль (Gradient Boosting), без LLM | Уже обосновано в §1.3.1, §2.3.3 — не предмет данного раздела |
| L5 | Генерация объяснения рекомендации | Закрытый (фиксированная структура: факторы + SHAP + доза + эффект) | **Шаблонная генерация текста** (заполнение заготовленных формулировок числами), LLM — опционально для более гибкой формулировки | Ноль риска галлюцинации при уже посчитанных детерминированных фактах; шаблон надёжнее и дешевле |
| L6 | Диалоговый ассистент агронома (произвольные вопросы) | **Открытый** | LLM-агент с function calling поверх API L2/L4/L5 | Единственный модуль, где вход принципиально не перечислим заранее — здесь LLM оправдана, а не факультативна |

## 2.5.3. Схемы function calling совпадают со свойствами онтологии

Там, где LLM всё же применяется (эволюция онтологии, диалоговый ассистент), схемы вызываемых инструментов **дословно повторяют** сигнатуры уже реализованных функций из `src/ds_ontology/integration.py` (которые, в свою очередь, реализуют `R_O`/`R_D` из §2.1.3). Это не отдельный слой промпт-инжиниринга, а прямое переиспользование уже формализованного словаря онтологии в качестве контролируемого выходного формата LLM.

## 2.5.4. Требования к дообучаемым моделям

### NER (RuBERT)

| Параметр | Значение | Обоснование |
|---|---|---|
| Базовая модель | `DeepPavlov/rubert-base-cased` (осн.) / `cointegrated/rubert-tiny2` (лёгкий вариант для локального инференса) | Русскоязычные модели с открытыми весами, уже названы как кандидаты в `docs/datasets.md` |
| Задача | Token classification, схема разметки BIO | Метки сущностей соответствуют классам §2.1.3: `KULTURA`, `AGROPRIEM`, `POKAZATEL`, `VREDITEL` |
| Learning rate | 2e-5 | Стандартная рекомендация для дообучения BERT-подобных моделей (Devlin et al., 2018) |
| Batch size | 8-16 (ограничено размером корпуса) | Малый корпус (100-200 предложений) не требует и не позволяет больших батчей |
| Эпохи | 10-20, с ранней остановкой по валидационному F1 (patience 3-5) | Малые корпуса требуют больше эпох для сходимости; ранняя остановка защищает от переобучения |
| Optimizer | AdamW, weight decay 0.01, warmup ratio 0.1 | Стандартная конфигурация для fine-tuning трансформеров |
| Max sequence length | 128 токенов | Агрономические предложения короткие; экономит память |
| Метрика отбора модели | F1 по сущностям (seqeval), а не accuracy по токенам | Accuracy завышена классом `O` (не-сущность), доминирующим в разметке |
| Данные | Ручная разметка `docs/datasets.md` (текстовые источники) | Датасет ещё не создан — скрипт рассчитан на формат, создание корпуса — отдельная задача |

### Классификатор поражений (EfficientNet/ResNet)

| Параметр | Значение | Обоснование |
|---|---|---|
| Базовая модель | `efficientnet_b0`, веса `EfficientNet_B0_Weights.IMAGENET1K_V1` (torchvision) — **используются по умолчанию** (`--no-pretrained` только как офлайн-резерв) | Transfer learning с ImageNet даёт кардинально лучшую сходимость на малых датасетах (PlantDoc — 2578 фото) по сравнению со случайной инициализацией; хороший баланс точности/размера для инференса на мобильном устройстве |
| Нормализация входа | `mean=[0.485,0.456,0.406], std=[0.229,0.224,0.225]` (статистика ImageNet) | Обязательна при использовании предобученных весов — иначе распределение пикселей не соответствует тому, на котором калибровались фильтры backbone |
| Learning rate | 3e-4 (голова), 1e-5 (backbone при разморозке) | Стандартная двухфазная схема transfer learning: сначала обучается только голова, затем fine-tuning всей сети на малом LR — так предобученные признаки не разрушаются слишком быстро |
| Batch size | 32 | Стандартное значение для классификации изображений на GPU/CPU среднего класса |
| Эпохи | Фаза 1 (заморож. backbone): 10; фаза 2 (полное дообучение): 20-30, ранняя остановка по валидационной accuracy | Разморозка backbone позже экономит время и снижает риск катастрофического забывания предобученных признаков |
| Аугментация | случайный поворот, отражение, изменение яркости/контраста | Стандартный набор для полевых фотографий (разный угол съёмки, освещение) |
| Данные | PlantDoc (CC BY 4.0, подтверждена) — `docs/dataset_cards/plantdoc.md`. PlantVillage — **не используется до подтверждения лицензии** (`docs/governance/licenses.md`) | Скрипт рассчитан на формат `ImageFolder` (train/ + test-или-val/ — см. `--val-subdir`), данные подключаются через `--data-dir` |

## 2.5.5. Требования к инфраструктуре обучения

- **NER**: обучение на CPU реально (малый корпус, компактная модель) за 10-30 минут; GPU ускоряет, но не обязателен.
- **Классификатор изображений**: обучение на полном PlantVillage (~54 тыс. изображений) практично только на GPU (несколько часов на одну GPU уровня T4/3060 для полной схемы с разморозкой); на CPU — только smoke-тест на малой выборке для проверки корректности пайплайна.
- Оба скрипта фиксируют `seed` для воспроизводимости и сохраняют лучший чекпоинт по валидационной метрике, а не по последней эпохе.

## 2.5.6. Наблюдаемость обучения: чекпоинты и метрики в прямом эфире

Оба скрипта пишут `history.json` рядом с чекпоинтом модели **после каждой эпохи**, а не только по завершении всего прогона — поле `status` принимает значение `"running"` во время обучения и `"completed"` после. Это отличает наблюдаемость от простого логирования в stdout: `service/routers/training_stats.py` читает тот же файл и отдаёт его состояние двумя способами —

- `GET /training/history` — разовый снимок (текущее содержимое `history.json` по обоим прогонам);
- `GET /training/history/stream` — SSE-поток: сервер раз в секунду сравнивает файл с предыдущим снимком и, если он изменился (т.е. скрипт обучения дописал очередную эпоху), немедленно отправляет клиенту новое событие.

Фронт (`frontend/src/pages/TrainingPage.tsx`) подключается к SSE-потоку через `EventSource` при открытии вкладки «Обучение» — графики loss/accuracy/F1 и индикатор «обучение идёт» обновляются сами по мере того, как процесс обучения (запущенный отдельно, например в контейнере `train`) дописывает эпохи, без перезагрузки страницы и без отдельного запроса от пользователя. `EventSource` браузера не умеет слать кастомные заголовки, поэтому опциональный API-ключ (`docs/chapter2/integration_model.md`, §2.6.4) для этого маршрута дополнительно принимается через query-параметр `?api_key=`.

**NER**: чекпоинты фиксируются через `TrainerCallback` (`on_evaluate`, т.к. `eval_strategy="epoch"`), в дополнение к штатному сохранению лучшей модели HuggingFace Trainer (`load_best_model_at_end`, `metric_for_best_model="f1"`). **Классификатор изображений**: `history.json` перезаписывается вручную в конце каждой итерации цикла обучения, синхронно с сохранением `best_model.pt` при улучшении `val_acc`.

## 2.5.7. Связь с реализацией

`training/finetune_ner.py`, `training/finetune_leaf_classifier.py` — см. докстринги файлов для точного набора аргументов командной строки. Оба скрипта содержат smoke-тест на игрушечных встроенных данных (без внешних датасетов) — подтверждает работоспособность пайплайна независимо от статуса лицензий реальных датасетов.

## Выводы

Раздел 2.5 формализует принцип «задача определяет инструмент»: LLM применяется только там, где вход задачи принципиально открытый (L6, редкие случаи эволюции онтологии в L2) — во всех остальных точках интеграции (детекция по фото, NER, генерация объяснений) специализированная дообученная или шаблонная модель точнее, дешевле и не создаёт внешней зависимости, что напрямую поддерживает требование адаптивности к российской специфике (локальная работа без гарантированного интернета, §1.4.2).
