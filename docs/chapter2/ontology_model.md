# 2.1. Концептуальная модель интеграции гетерогенных агрономических данных на основе онтологического подхода

> Черновик раздела главы 2 диссертации. Соответствует задаче 2 и положению 1, выносимому на защиту. Реализует уровень L2 архитектуры (см. `docs/architecture` / артефакт «Архитектура DS»).

## 2.1.1. Формальное определение динамической онтологии

Под динамической онтологией предметной области понимается кортеж, изменяющийся во времени:

```
O_t = ⟨C, R_O, R_D, Ax, I, τ⟩
```

где на момент времени *t*:

- **C** — конечное множество классов (концептов) предметной области, например *Поле*, *Культура*, *ПоказательПочвы*;
- **R_O ⊆ C × C** — множество объектных отношений между классами (object properties), каждое отношение снабжено характеристиками (функциональность, транзитивность, наличие обратного отношения);
- **R_D: C → 2^Attr** — множество отношений «класс → атрибут» (data properties), где *Attr* — множество допустимых типов данных (число, строка, дата, геометрия);
- **Ax** — множество аксиом: иерархия классов (`rdfs:subClassOf`), дизъюнктность, ограничения кардинальности, эквивалентность (`owl:equivalentClass`), а также отношения `owl:sameAs` и `skos:closeMatch` для приближённых терминологических соответствий (см. 2.1.6);
- **I** — множество индивидов (экземпляров, ABox);
- **τ: I → C** — функция типизации, сопоставляющая каждому экземпляру его класс(ы).

Пара ⟨C, R_O, R_D, Ax⟩ образует TBox (терминологический уровень, схема знаний), пара ⟨I, τ⟩ — ABox (фактологический уровень, конкретные данные хозяйства). Разделение TBox/ABox существенно: обновление ABox (появление новых измерений) происходит непрерывно и не требует экспертной валидации, тогда как изменение TBox (новый класс, новое отношение) — событие, требующее контроля (см. 2.1.6).

Онтология выражается в фрагменте **OWL 2 DL**, что гарантирует разрешимость задачи проверки логической непротиворечивости (consistency checking) стандартными DL-ризонерами (HermiT, Pellet) и было учтено при выборе характеристик отношений в *R_O*.

## 2.1.2. Повторное использование существующих онтологических ресурсов

В соответствии с требованием 7 (масштабируемость и переносимость, §1.4.2) онтология не строится с нуля, а расширяет верхнеуровневые ресурсы, рассмотренные в §1.3.4:

| Внешний ресурс | Что заимствуется | Что достраивается локально |
|---|---|---|
| AGROVOC (FAO) | базовые концепты культур, агроприёмов, вредителей и их русскоязычные метки (`skos:altLabel@ru`) | связь этих концептов с конкретными экземплярами полей и измерений |
| Crop Ontology | фенологические стадии, шкалы признаков культур | привязка стадии к конкретной дате/полю |
| BioAGgressor Ontology (BAGO) | таксономия патогенов и вредителей | связь «культура — риск поражения — дата обнаружения» |

Такое повторное использование снимает часть критики из §1.3.4 (статичность и трудоёмкость самостоятельной разработки онтологии с нуля) и одновременно требует надстройки — единственное, чего готовые ресурсы не содержат, это самих экземпляров хозяйства и связей с числовыми/геопространственными данными. Именно эта надстройка и есть научная новизна метода (новизна п. 1 введения).

## 2.1.3. Базовые классы предметной области

Минимальный набор классов, достаточный для связывания текстового отчёта, показания сенсора и картографического слоя вокруг одного поля (соответствует диаграмме `classDiagram` в §2.3.3 архитектурного документа):

| Класс | Источник | Ключевые атрибуты (R_D) | Ключевые отношения (R_O) |
|---|---|---|---|
| `Поле` | локальный | id, геометрия (WKT), площадь, регион | `выращивается→Культура`, `характеризуется→ПоказательПочвы`, `подвержено→ПогодноеСобытие`, `обрабатывается→АгроПриём` |
| `Культура` | AGROVOC + Crop Ontology | название, сорт, фенофаза | `подвержена→ВредительБолезнь` |
| `ПоказательПочвы` | AGROVOC (единицы измерения) | тип, значение, дата_измерения, ед_измерения | `зафиксирован_в→Источник` |
| `ПогодноеСобытие` | локальный (расширение) | тип, интенсивность, период | — |
| `АгроПриём` | AGROVOC (ветвь agricultural practices) | тип_операции, доза, дата | `описан_в→Источник` |
| `ВредительБолезнь` | BAGO + AGROVOC | название, стадия_риска | — |
| `Источник` | локальный | тип, формат, достоверность | — |

Класс `Поле` выступает **якорной сущностью** (anchor entity): каждый факт из любого источника данных в конечном счёте присоединяется к графу через отношение с конкретным экземпляром `Поле`, что и обеспечивает возможность комплексного (а не покомпонентного) анализа, недоступную ни статистическим методам, ни ГИС по отдельности (см. сводную таблицу §1.3.5).

## 2.1.4. Механизм семантической интеграции гетерогенных источников

Пусть `S = {s_1, …, s_n}` — множество источников данных согласно классификации §1.1.2 (сенсоры, ДЗЗ, телеметрия, лабораторные анализы, текст). Для структурированных и полуструктурированных источников с локальной схемой `σ_i` вводится **функция отображения схемы**:

```
φ_i : σ_i → (C ∪ R_O ∪ R_D)
```

устанавливаемая один раз для каждого типа источника (типа сенсора, типа лабораторного показателя и т. п.) и определяющая, в какой класс, атрибут или отношение онтологии превращается каждое поле исходной схемы.

Для неструктурированных текстовых источников `T_i` интеграция двухшаговая:

1. **NER**-модель извлекает упоминания сущностей `e` (текстовые спаны) с предсказанным типом класса;
2. **функция связывания сущностей** `λ: e → I ∪ {new}` либо сопоставляет упоминание существующему экземпляру (по строковому/эмбеддинговому сходству и ограничениям соседства в графе — например, «внесение произведено на поле №7» разрешается однозначно, если в тексте ранее упомянуто поле №7), либо порождает новый экземпляр.

Общая интеграционная функция:

```
μ = φ ∪ λ : D → I,   D = D_num ∪ D_geo ∪ D_text
```

где `D` — универсум гетерогенных данных из таблицы 1.1 главы 1. Именно `μ` формально закрывает разрыв, обозначенный в §1.3.5 как «разрыв между количественными данными и экспертными знаниями»: результатом её работы всегда является триплет `(Поле_i, предикат, значение)`, независимо от того, из какого по природе источника получено значение.

### Расширение на изображения и голосовые записи

Помимо `D_num`, `D_geo`, `D_text`, реальный поток агрономических данных включает **фотографии** (снимки с телефона агронома, кадры с камер техники — признаки поражения болезнью, состояние листа) и **голосовые записи** (полевые диктофонные заметки). Формально универсум данных расширяется до:

```
D = D_num ∪ D_geo ∪ D_text ∪ D_img
```

Здесь важно архитектурное решение: **голосовые записи не образуют отдельную модальность `D_audio`**, а сводятся к `D_text` через отдельный шаг распознавания речи (ASR) на уровне сбора (L1), после чего проходят тот же NER-конвейер и функцию `λ`, что и письменный текст. Это оправдано тем, что содержательная ценность голосовой заметки агронома («на седьмом поле пятна на листьях пшеницы») — в её текстовом содержании, а не в акустических характеристиках голоса; выделение акустических признаков как отдельной модальности усложнило бы модель без выигрыша для решаемых задач (прогноз урожайности, поддержка решений).

Для изображений вводится отдельная функция отображения:

```
φ_img : image → (C ∪ R_O ∪ R_D)
```

реализуемая моделью компьютерного зрения (детекция/классификация признаков поражения), результат которой — предсказанный класс и оценка серьёзности — так же, как и текстовые сущности, связывается функцией `λ` с существующим или новым экземпляром класса `ВредительБолезнь` (§2.1.3), с привязкой к экземпляру `Поле` по метаданным снимка (геометка, время, либо явное указание в сопроводительном тексте). Таким образом, фотография не порождает нового типа сущности в онтологии — она лишь ещё один источник наблюдений (`Источник` с `тип_источника = "фото"`) для уже определённых классов, что сохраняет модель типизации `τ: I → C` неизменной при добавлении новых каналов сбора данных.

## 2.1.5. Разрешение терминологической вариативности

Для класса `c ∈ C` определяется множество синонимов:

```
Syn(c) = {t_1, …, t_k}
```

— включающее литературный термин, региональные варианты и наследие советской агрономической школы (§ Введение, «семантический вакуум»). Термины хранятся как `skos:prefLabel` / `skos:altLabel` с языковой пометкой `ru`. Функция разрешения термина к классу:

```
resolve: (термин, контекст) → C ∪ {⊥}
```

реализуется как сходство по множествам `Syn`, дополненное для полисемичных терминов эмбеддинговым сходством и ограничениями графового соседства. Для близких, но не тождественных понятий (случай, детально разобранный в работе Aubin et al., 2024 при выравнивании онтологий признаков пшеницы, §1.3.4) вместо `owl:equivalentClass` используется более слабое отношение `skos:closeMatch`, фиксирующее неполную эквивалентность и требующее эксперта при спорных случаях.

## 2.1.6. Механизм эволюции онтологии (динамичность)

Обновление онтологии описывается операцией:

```
O_{t+1} = O_t ⊕ ΔO_t,   ΔO_t = (ΔC_t, ΔR_t, ΔAx_t, ΔI_t)
```

- `ΔI_t` (новые факты: показания сенсоров, новый спутниковый снимок, новая запись агроприёма) добавляется **автоматически** через `μ` без вмешательства эксперта — это рутинное пополнение ABox;
- `ΔC_t, ΔR_t, ΔAx_t` (новый класс, новое отношение, новая аксиома — например, появление нового препарата или ранее не описанного фитосанитарного события) добавляется **полуавтоматически**: кандидат предлагается конвейером извлечения терминов из новых текстовых источников, затем проходит через функцию валидации

```
V: ΔO_t^candidate → {accept, reject, modify}
```

выполняемую экспертом-агрономом. Такое разделение — единственный способ одновременно удовлетворить требованию 4 (интерпретируемость и контролируемость знаний) и требованию 8 (сквозной, а не батчевый характер обработки), не скатываясь в неконтролируемое автоматическое разрастание TBox, которое сделало бы онтологию логически противоречивой.

## 2.1.7. Связь с реализацией

Формальная модель `O_t = ⟨C, R_O, R_D, Ax, I, τ⟩` реализуется средствами OWL 2 DL через библиотеку **owlready2** (Python): классы `C` — как `owlready2.Thing`-наследники, `R_O`/`R_D` — как `ObjectProperty`/`DataProperty`, `Ax` — как декларации `is_a`, `equivalent_to`, ограничения через `Restriction`, консистентность `Ax` относительно `I` проверяется вызовом ризонера HermiT (`sync_reasoner()`). Код — в `src/ds_ontology/` (см. `docs/datasets.md` для источников наполнения `I` и README пакета).

## Выводы

Формализация раздела 2.1 даёт три вещи, необходимые для дальнейших глав: (1) точный контракт между источниками данных и графом знаний (функция `μ`), которым будут пользоваться модули L3–L5; (2) механизм снятия терминологической вариативности `resolve`/`Syn`, специфичный для российского агроконтента; (3) управляемый механизм эволюции `⊕`, отличающий предлагаемый подход от статических онтологий, раскритикованных в §1.3.4–1.3.5.
