# Отраслевые best-practices, принятые в проекте

Черновик методологического раздела (глава 2, вводная часть перед §2.1). Фиксирует, какие устоявшиеся отраслевые практики и стандарты сознательно приняты в архитектуре — а не изобретены заново — и где именно они применены.

## 1. FAIR-принципы данных (Findable, Accessible, Interoperable, Reusable)

Уже упомянуты в главе 1 (Soares, 2025, §1.4.1) как требование к семантической интероперабельности. В проекте операционализированы конкретно:

- **Findable** — каждый источник в `docs/datasets.md` снабжён прямой ссылкой;
- **Accessible** — указан способ доступа (API, SPARQL endpoint, RDF-дамп);
- **Interoperable** — данные приводятся к единой онтологии (§2.1) до попадания в аналитические модули;
- **Reusable** — лицензия и статус проверки фиксируются в `docs/governance/licenses.md` для каждого актива без исключений.

## 2. Model Cards и Datasheets for Datasets

Приняты как стандартная форма документирования каждой модели и каждого датасета в проекте — по аналогии с индустриальной практикой (Model Cards for Model Reporting, Datasheets for Datasets — устоявшиеся форматы документирования моделей и данных, принятые как стандарт в крупных ML-практиках Google/HuggingFace).

Правило: **новая модель или датасет не считается интегрированной в проект без заполненной карточки** в `docs/model_cards/` или `docs/dataset_cards/` (шаблоны там же). Это то же требование, что и для лицензий (`docs/governance/licenses.md`) — документирование не постфактум, а условие включения.

## 3. ISO 11783 (ISOBUS) / ISO-XML для карт-заданий

L5 экспортирует результат оптимизации (`docs/chapter2/optimization_model.md`, §2.4.6) в формате, совместимом с ISO 11783 (ISOBUS) — действующим отраслевым стандартом обмена данными между системами управления фермой и бортовыми терминалами сельхозтехники. Выбор не произвольный: без совместимости с ISOBUS карта-задание из L5 физически не попадёт на технику ни одного крупного производителя (John Deere, Claas, Case IH и т. д. поддерживают ISOBUS как общий знаменатель).

## 4. Соответствие архитектурным решениям реальных систем (глава 1, §1.3.3)

Две детали архитектуры прямо заимствуют устоявшиеся решения промышленных СППР, уже разобранных в главе 1:

- **Деградация к одному источнику при нехватке данных** (§2.2.5, комбинированный алгоритм L3: при отсутствии временной истории — только пространственная оценка, и наоборот) — тот же принцип, что в модуле *Sensorless Irrigation* платформы xFarm (§1.3.3): если нет выделенного датчика, показатель оценивается по спутниковым данным, а не блокирует работу системы.
- **Разделение на уровни сбора / моделирования / принятия решений** (L2/L4/L5) — та же структура, что в *Hydro-Tech DSS* (§1.3.3): Data Assimilation → Model Engine → Decision Maker. Совпадение не случайно: это типовая, проверенная практикой декомпозиция, а не изобретение с нуля.

## 5. Обязательная проверка лицензии перед использованием любого внешнего актива

Введено по итогам практической проверки (см. `docs/governance/licenses.md`): при подборе открытых данных для L1/L4 обнаружено, что широко используемый в академических работах датасет PlantVillage не имеет явно опубликованной лицензии, а зеркало датасета Kaggle на GitHub (Harvestify) распространяется в GPL-3-репозитории без подтверждённой лицензии на сами данные. Оба актива исключены из использования до прояснения статуса — это правило, а не исключение: «широко используется» не равно «имеет открытую лицензию».
